# 개발하면서 마주친 문제

기능이 정상 동작하는지만 보는 것보다, **왜 문제가 생겼고 비슷한 문제가 다시 발생하지 않게 하려면 무엇을 바꿔야 하는지**를 기록하려고 합니다.

## 1. IntelliJ에서 프로젝트 실행 설정이 맞지 않았던 문제

새 프로젝트를 실행하는 과정에서 JDK 설정이 맞지 않아 애플리케이션을 실행하지 못했습니다.

Java 버전을 선택했다고 해서 IntelliJ의 프로젝트 SDK와 실행 구성에 자동으로 같은 설정이 적용되는 것은 아니었습니다. 프로젝트 SDK와 실행할 JDK를 다시 맞추고, 실행 대상 메인 클래스를 `com.communityplatform.CommunityPlatformApplication`으로 지정했습니다.

환경변수도 소스 코드에 직접 적는 것이 아니라 실행 구성에서 주입하도록 정리했습니다.

개발을 시작할 때는 단순히 언어 버전만 맞추는 것이 아니라 **빌드 도구, 프로젝트 SDK, 실행 구성에서 실제 사용하는 JDK**를 함께 확인해야 한다는 점을 다시 확인했습니다.

## 2. Discord 봇을 초대했는데 역할이 보이지 않았던 문제

Discord 봇을 서버에 추가했지만 기대했던 봇 역할이 보이지 않아 설정을 확인했습니다.

처음에는 봇을 초대하면 필요한 역할도 모두 자동으로 생성될 거라고 생각했습니다. 하지만 봇 설치, 서버 내 역할, 역할의 순서, 봇이 요청한 권한, Gateway Intent는 서로 다른 설정이었습니다.

특히 멤버 목록 조회에는 `Server Members Intent`를 확인해야 하고, 멤버를 관리하거나 추방하려면 Discord 서버에서 봇 역할의 권한과 계층도 맞아야 합니다.

이 문제를 계기로 **봇이 서버에 설치되어 있는지**와 **그 봇이 실제로 해당 작업을 수행할 권한이 있는지**를 따로 확인하도록 접근했습니다.

## 3. 닉네임으로 회원을 연결하면 생길 수 있는 문제

Discord 멤버 목록을 웹서비스 회원과 연결할 때 가장 간단한 방법은 닉네임 비교였습니다. 하지만 Discord 표시명은 언제든 변경할 수 있고 다른 사람과 같아질 수도 있습니다.

클랜원을 잘못 연결하면 단순한 화면 오류에서 끝나지 않고 회원 권한이나 활동 기록까지 잘못된 계정에 연결될 수 있습니다.

이 문제를 피하려고 **Discord 사용자 ID를 연결의 기준**으로 정했습니다.

서비스에 로그인한 Discord 계정의 ID와 동기화된 서버 멤버의 ID가 정확히 일치할 때만 연결합니다. 여기에 현재 서버 소속, 지정 역할, 활성 상태를 확인하고 기존 운영진 권한이나 탈퇴 기록을 덮어쓰지 않도록 했습니다.

코드에서는 자동 연결 조건과 예외 상황을 점검했습니다. 실제 Discord 서버와 연동했을 때의 동작은 계속 확인할 예정입니다.

## 4. 추방 요청이 실패한 것인지, 결과만 모르는 것인지

이 문제는 이전 프로젝트인 **GuildUp**에서 닉네임 기준 자동 추방 기능을 작업하며 다뤘습니다.

처음에는 추방 API 호출을 시도했으면 요청이 전송됐다고 생각하기 쉬웠습니다. 하지만 요청을 전송하기 전에 취소한 경우와, 전송은 됐을 수 있지만 응답을 확인하지 못한 경우는 전혀 다릅니다.

둘을 같은 실패로 처리하면 이미 추방됐을 수도 있는 사용자를 다시 추방하려고 시도하는 등 중복 조치가 발생할 수 있습니다.

이를 구분하기 위해 다음처럼 상태를 나눴습니다.

- `SKIPPED`: 요청이 실제로 전송되기 전에 취소됨
- `PENDING`: 처리 결과를 기다리는 중
- `UNKNOWN`: 요청이 전송됐을 가능성은 있지만 결과를 확인하지 못함

전송 전 취소는 짧은 시간 동안 중복을 억제하고, 결과가 불분명한 작업은 자동 재시도를 신중하게 다루도록 했습니다.

community-platform에서는 이런 경험을 바탕으로 **관리자 승인, 중복 조치 방지, 실행 결과 기록**을 운영 기능 설계에 반영하고 있습니다. 이는 GuildUp에서 해결했던 문제를 소개한 것이며, 새 프로젝트의 추방 기능이 완성됐다는 뜻은 아닙니다.

## 5. PUBG만 생각하고 만들면 다른 게임을 추가하기 어려운 문제

기존 클랜이 PUBG를 이용하다 보니 처음에는 PUBG 중심으로 기능을 만들기 쉬웠습니다.

하지만 게임마다 계정 식별 방식, API, 경기 기록 형태, 활동 판정 기준이 다릅니다. 심지어 같은 PUBG도 Kakao와 Steam을 구분해야 합니다.

그래서 모든 커뮤니티에 PUBG 필드를 붙이기보다, **커뮤니티 공통 정보와 게임별 연동 데이터를 구분**하는 방식으로 방향을 잡았습니다.

현재는 PUBG를 먼저 다루고 있지만, 다른 게임을 추가할 때 공통 회원 관리와 권한 구조를 크게 바꾸지 않는 것이 목표입니다. 실제 다른 게임의 연동까지 검증한 단계는 아닙니다.

## 6. 짧은 킬내기에도 오래된 경기를 계속 조회했던 문제

킬내기 결과를 실제 PUBG 데이터로 처음 조회했을 때, 집계에 필요한 경기는 3판이었지만 참가자 네 명의 경기 상세를 442건 받아 왔습니다. 플레이어별 경기 목록에 날짜 필터가 없어서 어느 경기가 대회 기간에 속하는지 상세 정보의 시작 시각을 보고 판단해야 했습니다.

실제 응답에서 경기 목록이 대체로 최신순으로 오는 것을 확인했습니다. 이미 저장한 경기의 시작 시각은 다시 쓰고, 대회 시작보다 오래된 경기를 만나면 세 경기를 더 확인한 뒤 멈추도록 바꿨습니다. 확인 구간에 대회 기간에 속하는 경기가 다시 나오면 그 참가자의 목록은 끝까지 조회합니다.

수정 뒤 테스트 DB에서 실시한 실제 PUBG 확인 조회에서는 목록에 있던 596건 중 상세 13건을 받아 왔습니다. 앞선 조회와는 실행 시점이 달라 목록에 포함된 경기도 달랐습니다. 두 번째 조회에서는 첫 조회 때 진행 중이던 경기까지 올라와, 대회 마감 전에 시작한 경기는 마감 뒤에 끝나도 집계되는 것을 확인했습니다.

## 7. Discord에서 바꾼 닉네임이 실시간으로 반영되지 않았던 문제

Discord에서 닉네임을 변경하면 웹의 클랜원 목록에는 예전 이름이 남았습니다. 수동으로 클랜원을 가져오면 새 이름이 나타나서, 서버 목록을 조회하는 REST 요청과 실시간 이벤트를 받는 Gateway 연결을 따로 살펴봤습니다.

실행 중인 백엔드의 클래스패스와 Maven이 만든 클래스패스를 비교해 보니, VS Code 실행 환경에 JDA의 새 런타임 의존성이 빠져 있었습니다. 연결을 시작할 때 발생한 클래스 로딩 오류가 예약 작업 안에 남아서 로그가 보이지 않았고, 상태는 계속 연결 중으로 남았습니다.

누락된 클래스가 있으면 오류 이유를 로그에 남기고 연결 실패 상태로 전환하도록 수정했습니다. 같은 오류를 재현한 테스트가 수정 뒤 통과했고, IDE 프로젝트를 다시 불러온 뒤 실제 서버에서 닉네임 변경이 반영되는지 확인하는 작업이 남아 있습니다.

## 8. 실제 경기 기록과 빙고 미션 판정이 어긋났던 문제

빙고에는 경기 상세의 공식 통계로 확인할 수 있는 미션과 경기 중 이벤트를 읽어야 하는 미션이 함께 있습니다. 실제 경기 데이터를 살펴보니 낙하산 거리는 예상한 센티미터 단위가 아니었고, 화염병 킬은 무기 코드만으로 잡히지 않는 경우가 있었습니다.

실제 값에 맞춰 낙하산 거리와 화염병 처치 이벤트 해석을 수정하고, 확인한 사례를 테스트에 추가했습니다. 벽 관통 킬처럼 표본에서 성공 사례를 확인하지 못한 미션은 편집기에서 숨겼습니다.

## 9. 킬내기와 빙고가 같은 경기 데이터를 사용할 때

킬내기를 위해 저장한 경기 정보에는 킬과 등수만 있어도 됩니다. 하지만 빙고에서는 피해량이나 아이템 사용 기록까지 필요합니다. 기존 저장 데이터가 있다는 이유로 API 조회를 생략하면 빙고에서는 필요한 항목이 빠질 수 있습니다.

처음에는 경기 통계 수집 여부를 참·거짓으로 관리했지만, 기능이 추가되면서 이 값만으로는 어떤 통계가 있는지 구분하기 어려워졌습니다. 그래서 통계 상태를 버전으로 바꿨습니다. 킬·등수까지만 수집한 경기와 빙고용 상세 통계까지 수집한 경기를 구분해, 필요한 경우에만 더 자세한 데이터를 가져오도록 했습니다.

경기 수집기는 킬내기와 빙고가 같이 사용하도록 분리했습니다. 새로운 기능이 생겨도 경기 목록을 조회하고 저장하는 코드를 각 기능에 복사하지 않기 위한 선택입니다.

## 10. 이벤트 보상을 다시 처리하면 점수가 두 번 쌓일 수 있는 문제

킬내기 결과 정산은 외부 API 조회가 실패하거나 서버가 재시작되면 다시 실행될 수 있습니다. 단순히 우승자에게 점수를 더하는 방식이라면 같은 결과를 두 번 처리했을 때 점수가 중복 지급될 수 있습니다.

랭킹 점수에는 변경 사유와 함께 같은 지급 건을 식별할 키를 저장합니다. DB에서도 커뮤니티와 해당 키의 조합을 유일하게 관리하고, 점수 행을 잠근 상태에서 이력과 총점을 함께 갱신하도록 했습니다.

이 방식을 사용하면 랭킹 화면에서는 누적 점수를 빠르게 조회하면서도, 나중에 어느 이벤트에서 점수가 지급됐는지 확인할 수 있습니다. 비슷한 점수 지급 기능이 추가되더라도 같은 규칙을 재사용할 수 있습니다.

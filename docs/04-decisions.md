# 설계 선택과 의사결정

## 이전 GuildUp을 그대로 복사하지 않은 이유

기존 구현은 Discord와 PUBG 데이터를 연결하는 가능성을 확인하는 데 도움이 됐습니다. 그러나 확장 가능한 커뮤니티 플랫폼을 목표로 하면 회원/클랜원/외부 계정의 경계, 운영 정책, 승인 조치와 외부 API 실패에 대한 처리를 다시 정의할 필요가 있었습니다.

## 핵심 결정과 근거

| 결정 | 이유 | 주의 사항 |
| --- | --- | --- |
| Java 21 + Spring Boot | 익숙한 백엔드 생태계에서 도메인·인증·외부 연동 개발 | 자동 테스트와 운영 검증 분리 |
| React + TypeScript + Vite | 커뮤니티별 관리 화면과 API 통합 | 배포·캐시 전략 별도 검토 |
| 모듈러 모놀리스 | 초기 운영 규모에서 배포 단순성을 유지하며 경계 명시 | 모듈 인터페이스 준수 검사 필요 |
| Spring Modulith | 모듈 의존성을 코드 수준에서 검증하려는 목적 | 설치·실제 검증 결과를 별도로 기록 |
| 커뮤니티당 게임 하나 | 운영 정책과 게임별 기능 범위를 명확화 | 타 게임 확장 시 연동 플러그인 경계 필요 |
| Discord 사용자 ID 기반 연결 | 표시명 변경·중복 매칭 방지 | Discord 연결과 클랜 명부 동기화 확인 |
| 자동 조치보다 운영자 승인 | 추방·권한 변경의 피해와 오판 방지 | 실행·실패·결과 불명 상태 모델링 |

## 설계 기록에서 특히 중요했던 선택

이전 아키텍처 초안은 `shared`, `audit`, `identity`, `community`, `membership`, `integration`, `activity`, `operation` 모듈을 제안했습니다. 모듈 순환 참조를 피하기 위해 **권한 판정 계약**과 **외부 조치 실행 계약**을 분리하는 방향이었습니다. 이것은 초기 **설계 기록**으로서, 현재 코드에 각 모듈이 완성되어 있다는 증거는 아닙니다.

또한 접근 역할, 분류, 명부 상태, 활동 상태를 별도 축으로 다루는 검토가 있었습니다. 다만 현행 요구사항에서는 별도 게스트 역할을 제외했으므로, 과거의 게스트 분류 초안을 현재 확정 스펙처럼 반영하지 않습니다.

**미결 또는 검증 필요:** DB 기본키 전략, RLS 적용 여부, 비동기 작업의 잠금 방식, 실제 모듈 경계 검증 결과. 제안된 ADR을 구현 완료로 표시하지 않습니다.

# 기술 선택과 설계 고민

## 왜 처음부터 다시 만들었나

GuildUp을 개발하면서 Discord와 PUBG 데이터를 연동하고 운영 기능을 구현해볼 수 있었습니다. 다만 하나의 클랜에 맞춰 기능을 추가하다 보니, 다른 커뮤니티나 게임에서도 사용할 서비스를 만들려면 정보의 경계를 더 명확하게 잡아야겠다고 생각했습니다.

이번에는 화면과 기능을 빨리 늘리는 것보다 **어떤 데이터를 누가 소유하고, 어디에서 권한을 확인하며, 외부 연동이 실패하면 어떻게 처리할지**를 먼저 고민했습니다.

## 모듈러 모놀리스를 선택한 이유

초기 규모에서 서비스를 여러 개로 분리하면 배포와 운영이 복잡해질 수 있습니다. 반대로 기능을 하나의 프로젝트 안에 아무 구분 없이 넣으면 의존성이 꼬이기 쉽습니다.

그래서 배포는 하나로 유지하되 계정, 커뮤니티, 멤버십, 외부 연동, 활동 관리의 경계를 나누는 **모듈러 모놀리스**를 설계 방향으로 정했습니다.

Spring Modulith도 모듈 간 의존 관계를 점검하기 위한 도구로 검토했습니다. 중요한 것은 라이브러리 자체보다, 다른 도메인의 내부 구현을 직접 참조하지 않도록 경계를 지키는 것이라고 생각합니다.

## 커뮤니티 회원과 클랜원을 분리한 이유

Discord 서버에 속한 사람이 반드시 웹서비스에 가입한 것은 아닙니다. 웹서비스에 가입했다고 해서 모든 Discord 서버의 클랜원인 것도 아닙니다.

따라서 다음 정보를 각각 다루도록 했습니다.

- **서비스 사용자:** 로그인할 수 있는 계정
- **커뮤니티 회원:** 특정 커뮤니티에 가입해 가진 역할
- **Discord 클랜원:** 연동된 Discord 서버와 역할 기준으로 확인되는 사람
- **게임 계정:** 경기 기록을 조회할 대상

이 구분이 있어야 한 사람이 여러 커뮤니티에 가입하거나 Discord 표시명을 변경해도 잘못된 연결을 줄일 수 있습니다.

## 게임 선택을 커뮤니티 생성 시점에 두는 이유

서로 다른 게임은 필요로 하는 기능이 다릅니다. PUBG에서 중요한 경기·스쿼드 활동 정보가 다른 게임에서도 같은 의미는 아닐 수 있습니다.

그래서 커뮤니티마다 게임을 하나 선택하도록 하고, **회원 관리 같은 공통 기능과 게임 데이터 조회 같은 개별 기능**을 구분하려고 합니다.

현재 게임은 PUBG 중심이며 Kakao와 Steam도 구분합니다. 아직 다른 게임을 실제로 추가한 것은 아니므로, 이 구조가 모든 게임에서 그대로 통할 것이라고 단정하지는 않습니다.

## 자동 추방보다 승인 절차를 우선하는 이유

활동 기록이 부족하다고 해서 곧바로 추방하는 것은 위험합니다. API 조회 실패나 계정 매핑 오류 때문에 활동이 없다고 잘못 판단할 수 있기 때문입니다.

따라서 **활동 판정 → 운영진 확인 → 조치 실행 → 처리 결과 기록**을 분리하는 방향을 택했습니다.

특히 외부 API 요청은 실패 응답이 왔다고 해서 작업이 수행되지 않았다고 단정할 수 없습니다. 기존 GuildUp에서 다뤘던 결과 불명 문제를 고려해, 자동 조치에서는 중복 실행과 불확실한 응답을 별도로 다뤄야 한다고 생각합니다.

## 데이터베이스에서 고민한 부분

여러 커뮤니티가 같은 DB를 사용하면 다른 커뮤니티의 데이터를 잘못 참조하지 않는 것이 중요합니다.

커뮤니티 ID를 기준으로 조회·수정 범위를 제한하고, 연관 데이터에도 커뮤니티 경계를 드러내는 방법을 검토했습니다. 기본키 방식, 복합 외래키, RLS, 비동기 작업의 잠금 전략은 실제 구현과 운영 부담을 비교해 결정해야 할 부분으로 남겨 두었습니다.

모든 선택을 처음부터 정답으로 확정하기보다, 구현 과정에서 근거를 확인하고 조정할 수 있도록 기록하고 있습니다.

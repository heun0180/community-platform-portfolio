# 기술 선택과 설계 고민

## 왜 처음부터 다시 만들었나

GuildUp을 개발하면서 Discord와 PUBG 데이터를 연동하고 운영 기능을 구현해볼 수 있었습니다. 다만 하나의 클랜에 맞춰 기능을 추가하다 보니, 다른 커뮤니티나 게임에서도 사용할 서비스를 만들려면 정보의 경계를 더 명확하게 잡아야겠다고 생각했습니다.

이번에는 화면과 기능을 빨리 늘리는 것보다 **어떤 데이터를 누가 소유하고, 어디에서 권한을 확인하며, 외부 연동이 실패하면 어떻게 처리할지**를 먼저 고민했습니다.

## 모듈러 모놀리스를 선택한 이유

초기 규모에서 서비스를 여러 개로 분리하면 배포와 운영이 복잡해질 수 있습니다. 반대로 기능을 하나의 프로젝트 안에 아무 구분 없이 넣으면 의존성이 꼬이기 쉽습니다.

그래서 배포는 하나로 유지하되 계정, 커뮤니티, 멤버십, 외부 연동, 활동 관리의 경계를 나누는 **모듈러 모놀리스**를 설계 방향으로 정했습니다.

Spring Modulith를 도입해 모듈 간 순환 참조와 다른 모듈의 내부 패키지 접근을 자동 테스트로 검사합니다. 랭킹처럼 다른 기능에서 필요한 동작은 모듈의 공개 인터페이스로 제공합니다.

## 커뮤니티 회원과 클랜원을 분리한 이유

Discord 서버에 속한 사람이 반드시 웹서비스에 가입한 것은 아닙니다. 웹서비스에 가입했다고 해서 모든 Discord 서버의 클랜원인 것도 아닙니다.

따라서 다음 정보를 각각 다루도록 했습니다.

- **서비스 사용자:** 로그인할 수 있는 계정
- **커뮤니티 회원:** 특정 커뮤니티에 가입해 가진 역할
- **Discord 클랜원:** 연동된 Discord 서버와 역할 기준으로 확인되는 사람
- **게임 계정:** 경기 기록을 조회할 대상

이 구분이 있어야 한 사람이 여러 커뮤니티에 가입하거나 Discord 표시명을 변경해도 잘못된 연결을 줄일 수 있습니다.

## 게임 선택을 커뮤니티 생성 시점에 두는 이유

서로 다른 게임은 필요로 하는 기능이 다릅니다. PUBG에서 중요한 경기·스쿼드 활동 정보가 다른 게임에서도 같은 의미는 아닐 수 있습니다.

그래서 커뮤니티를 만들 때 게임과 플랫폼을 선택하도록 하고, **회원 관리 같은 공통 기능과 게임 데이터 조회 같은 개별 기능**을 구분했습니다. PUBG 경기 수집과 점수 계산은 PUBG 모듈에서 다루고, 커뮤니티 기능은 게임별 상세 규칙과 독립적으로 동작합니다.

현재 게임은 PUBG 중심이며 Kakao와 Steam도 구분합니다. 아직 다른 게임을 실제로 추가한 것은 아니므로, 이 구조가 모든 게임에서 그대로 통할 것이라고 단정하지는 않습니다.

## 자동 추방보다 승인 절차를 우선하는 이유

활동 기록이 부족하다고 해서 곧바로 추방하는 것은 위험합니다. API 조회 실패나 계정 매핑 오류 때문에 활동이 없다고 잘못 판단할 수 있기 때문입니다.

따라서 **활동 판정 → 운영진 확인 → 조치 실행 → 처리 결과 기록**을 분리하는 방향을 택했습니다.

특히 외부 API 요청은 실패 응답이 왔다고 해서 작업이 수행되지 않았다고 단정할 수 없습니다. 기존 GuildUp에서 다뤘던 결과 불명 문제를 고려해, 자동 조치에서는 중복 실행과 불확실한 응답을 별도로 다뤄야 한다고 생각합니다.

## 데이터베이스에서 고민한 부분

여러 커뮤니티가 같은 DB를 사용하면 다른 커뮤니티의 데이터를 잘못 참조하지 않는 것이 중요합니다.

조회와 수정은 요청한 커뮤니티의 ID와 회원 권한을 기준으로 제한했습니다. 회원·가입 신청과 랭킹처럼 커뮤니티에 속하는 데이터는 복합 외래키로 같은 커뮤니티의 행을 가리키도록 했습니다. 다른 커뮤니티의 ID를 넣어 접근하는 경우도 테스트로 확인합니다.

PostgreSQL의 행 수준 보안(RLS)은 운영 규모와 직접 SQL 조회 경로가 늘어날 때 다시 검토할 항목으로 남겼습니다.

## 경기 수집과 예약 처리 방식을 나눈 이유

클랜 활동 조회는 PUBG에서 경기 기록을 가져오는 데 시간이 걸립니다. 운영진 요청을 받으면 실행 기록을 만들고, 백그라운드에서 수집한 뒤 결과를 저장하도록 했습니다. 같은 경기의 기록을 여러 사람이 필요로 할 때는 저장된 경기 정보를 재사용할 수 있습니다.

킬내기의 마감과 최종 집계는 프로세스가 재시작돼도 다시 처리할 수 있어야 했습니다. 실행할 일과 시각을 대회 상태에 저장해 두고 주기적으로 확인합니다. 실행 중인 작업은 일정 시간 다른 실행이 가져가지 못하게 하고, 그 시간이 지나면 다시 처리할 수 있게 했습니다.

## 랭킹 점수를 이력으로 남기는 이유

킬내기 우승과 출석처럼 점수를 지급하는 기능이 늘어나면 총점만 봐서는 점수가 어디서 왔는지 알기 어렵습니다. 지급 이유와 변경량을 이력으로 저장하고, 월간 점수는 서울 시간 기준 해당 월의 이력으로 계산합니다.

같은 이벤트를 다시 처리해도 점수를 한 번만 반영하도록 지급 건마다 중복 확인에 사용할 키를 둡니다. 출석 기록과 1점 지급은 같은 트랜잭션에서 처리해, 출석만 기록되고 점수는 빠지는 상태를 피했습니다.

## Discord 이벤트와 전체 동기화를 함께 쓰는 이유

Discord에서 역할이나 닉네임이 바뀔 때마다 운영진이 전체 목록을 가져오기는 어렵습니다. 로컬 개발 버전에서는 백엔드와 같은 프로세스에 JDA Gateway 연결을 두고, 멤버 변경과 음성 상태 이벤트를 받아 처리하도록 했습니다.

연결이 끊기는 동안에는 이벤트가 빠질 수 있습니다. 앱을 다시 시작하거나 Discord 세션이 새로 만들어지면 기존 REST 전체 동기화로 클랜원 상태를 맞추고, 음성 세션은 마지막으로 관측한 시각을 기준으로 복구합니다.
